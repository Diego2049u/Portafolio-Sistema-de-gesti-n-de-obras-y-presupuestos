CONTRATO API MVP FYAG
====================

Este contrato describe el alcance implementado para preparar la API del MVP. Sustituye las referencias de inventario/Cardex de la documentación técnica anterior. La configuración de dependencias y base de datos se mantiene a cargo del equipo.

ALCANCE
-------
- Clientes y contratos.
- Catálogo administrable de categorías de servicio. Categorías iniciales: Proyecto, Mantención, Climatización, Proyecto eléctrico, Emergencia, Garantía y Mejoras. Venta de repuestos queda fuera por ahora.
- Presupuestos, partidas y PDF.
- Obras, costos directos, facturas, pagos y cierre comercial.
- Eventos de auditoría.
- Inventario, materiales de bodega y movimientos Cardex quedan fuera de este MVP.

AUTENTICACIÓN
-------------
- GET  /api/auth/csrf/       obtiene token CSRF.
- POST /api/auth/login/     recibe {"email", "password"}; emite cookies HttpOnly.
- POST /api/auth/refresh/   renueva cookies con el refresh token HttpOnly.
- POST /api/auth/logout/    revoca el refresh token y limpia cookies.
- GET  /api/auth/me/        devuelve identidad y rol de la sesión.
- Las escrituras requieren cookie de sesión y encabezado X-CSRFToken.

Acciones de presupuesto:
- POST /api/presupuestos/{id}/enviar/
- POST /api/presupuestos/{id}/aprobar-gerencia/ con {"decision":"aprobada"|"rechazada"}
- POST /api/presupuestos/{id}/decision-cliente/ con {"decision":"aprobado"|"rechazado"}
- GET  /api/presupuestos/{id}/exportar-pdf/

Acciones de obra:
- GET  /api/obras/presupuestos-disponibles/
- GET  /api/obras/tecnicos-disponibles/
- POST /api/obras/{id}/transicionar/ con {"estado_operativo":"finalizada"|"suspendida"|"cancelada"|"en-proceso"}
- POST /api/obras/{id}/cerrar-comercial/

Auditoría admite filtros `modulo`, `resultado` (exito, error, incompleto), `desde`, `hasta` y `q`.

REGLAS CENTRALES
----------------
- El presupuesto usa `estado` para el flujo con el cliente y `aprobacion_gerencia` para la autorización interna opcional.
- Una obra puede finalizar operativamente antes de cobrar. El cierre comercial requiere obra finalizada, al menos una factura y saldo cero en todas sus facturas.
- No se puede finalizar una obra sin técnico responsable ni cancelar una obra con pagos registrados.
- Los importes del presupuesto se calculan a partir de sus partidas; saldo y estado de factura se actualizan al registrar pagos.
- Los DELETE de recursos de negocio son borrados lógicos. No se permite eliminar una factura con pagos/saldo, un presupuesto vinculado a una obra ni una obra con facturas o gastos. Los pagos son inmutables por API.
- Los eventos de auditoría son append-only desde la API y solo Gerencia puede consultarlos.

RESUMEN DEL DASHBOARD
---------------------
El resumen está disponible para Gerencia y Finanzas. Si no se envían fechas, consulta desde el primer día del mes actual hasta hoy. El rango máximo es de 367 días calendario inclusive.
- `ventas_facturadas`: suma el monto total de las facturas emitidas en el periodo, no los pagos recibidos.
- `presupuestos_aprobados`: cuenta y suma presupuestos cuya decisión del cliente fue aprobatoria durante el periodo.
- `presupuestos_pendientes`: cuenta y suma presupuestos enviados al cliente o pendientes de aprobación de Gerencia, emitidos durante el periodo. Los borradores no cuentan como pendientes.
- `obras_en_proceso`: cuenta las obras que actualmente tienen estado operativo `en-proceso`; no reconstruye estados históricos.
- `servicios_realizados`: cuenta las obras finalizadas cuya fecha de término cae dentro del periodo.
- `costos_directos_periodo`: suma los registros activos de `CostoMaterial` fechados dentro del periodo. También se devuelve el desglose mensual y por categoría.
- `costos_por_obra_acumulados`: devuelve hasta diez obras con mayor gasto acumulado, presupuesto neto y porcentaje del presupuesto consumido. Esta medida usa el ciclo completo de la obra, no solo el periodo seleccionado.
- Las distribuciones devuelven obras por estado, servicios finalizados por categoría y facturación agrupada por mes.
- Los filtros de cliente, técnico y estado operativo restringen las obras y sus presupuestos, facturas y costos asociados. El filtro de estado no altera la definición de la métrica `obras_en_proceso`.
- No se calcula un KPI de margen: antes hace falta acordar el criterio de reconocimiento de ingresos, costos y periodo comparable.
- `moneda` es CLP y los importes se devuelven como enteros. En ausencia de resultados, las cantidades y montos son cero y las series son listas vacías.

CATÁLOGO INICIAL
----------------
Después de preparar/aplicar las migraciones del esquema, ejecutar:
  python manage.py seed_catalogs

MIGRACIONES
-----------
Los modelos son la definición del dominio, pero Django aplica archivos de migración. La migración inicial que ya está en el repositorio corresponde al esquema previo y debe reconciliarse con estos cambios, especialmente la conversión de categorías de texto a claves foráneas. No aplicar el esquema nuevo a una base con datos previos sin preparar la migración de datos correspondiente.

AJUSTES DE INTEGRIDAD Y SEGURIDAD (2026-11)
-------------------------------------------
- `ObraEstadoHistorial` conserva el estado inicial y cada transición con fecha y actor. Consultar con `GET /api/obras/{id}/historial-estados/`; el filtro de obras asignadas también aplica a técnicos.
- `GET /api/obras/tecnicos-disponibles/` devuelve `obras_activas` (obras asignadas en proceso o suspendidas). Es una medida de carga actual, no un calendario de disponibilidad.
- `Contrato` se puede enlazar opcionalmente desde `Presupuesto`; debe corresponder al mismo cliente y no se puede desactivar mientras tenga presupuestos vinculados.
- No se emiten presupuestos ni facturas si `Cliente.habilitar_emision` es falso. El historial sigue consultable.
- La suma de facturas activas de una obra no supera `Presupuesto.monto_total`; el alta serializa el control bloqueando la fila de obra.
- `POST /api/facturas/{id}/notas-credito/` recibe `numero`, `monto` y `motivo`. El monto reduce el saldo por cobrar y no puede superar el saldo vigente.
- `POST /api/pagos/{id}/reversas/` recibe `monto` y `motivo`. Registra una compensación sin alterar ni borrar el pago original; el total revertido no puede exceder el pago.
- Las entidades basadas en `SoftDeleteModel` guardan `created_at`, `updated_at`, `created_by` y `updated_by`.
- Throttling: API anónima 60 solicitudes/hora, autenticada 1200 solicitudes/hora, y login 5 intentos/minuto por IP.
- Gerencia mantiene bypass total de permisos, incluida la administración de usuarios. Supervisor opera obras y costos sin acceso al detalle financiero de presupuestos; puede asociar un presupuesto aprobado desde el endpoint reducido de disponibles. Esta separación sigue la matriz de roles acordada.
- El límite de facturación compara el total acumulado de facturas menos notas de crédito emitidas; permite re-facturar montos efectivamente acreditados sin sobrepasar el presupuesto aprobado.
- `ventas_facturadas.monto_total` del dashboard ahora es neto de notas de crédito emitidas en el periodo; también expone bruto, total acreditado y cantidades separadas.
- No se agregó exportación CSV ni Excel. Excel queda para una etapa posterior; el PDF de presupuestos existente se conserva.
- `Factura.estado_pago` admite `SALDADO` cuando el saldo llegó a cero por una nota de crédito; `PAGADO` queda reservado para saldo cubierto mediante pagos.
- Estado de migraciones a la fecha: la carpeta `backend/api/migrations/` fue eliminada por corresponder al ensayo SQLite anterior. Una vez cerrada esta revisión de modelos, generar una migración inicial nueva con `python manage.py makemigrations api` y aplicar `python manage.py migrate` sobre la base PostgreSQL objetivo.

WORKFLOWS Y DASHBOARD - AJUSTES (2026-11)
----------------------------------------
- Gerencia puede usar `POST /api/presupuestos/{id}/exigir-aprobacion-gerencia/` mientras el presupuesto siga en borrador. Finanzas crea y envía el presupuesto; si Gerencia exigió revisión, el envío queda en `pendiente_gerencia`. No existe un umbral monetario automático porque el negocio no ha definido ese monto.
- Un presupuesto rechazado por el cliente es terminal. Si el cliente solicita cambios se crea otro presupuesto; no se reabre ni se edita el rechazado.
- `GET /api/presupuestos/{id}/historial-versiones/` devuelve versiones inmutables con snapshots de los datos y partidas. Se registra la versión inicial y cada edición permitida en borrador.
- `fecha_vencimiento`, cuando se informa, debe ser posterior a la fecha de emisión.
- `numero_presupuesto`, `codigo_obra` y `numero_factura` son correlativos automáticos por tipo y año (`PRE-AAAA-######`, `OBR-AAAA-######`, `FAC-AAAA-######`); no se aceptan en el cuerpo de creación.
- No se puede cancelar una obra con facturas emitidas, estén pagadas o no. Suspensión y cancelación requieren `motivo`, que queda en el historial de estados.
- Una obra finalizada o cerrada comercialmente no admite cambios operativos ni nuevos/actualizados costos; solo se pueden corregir observaciones técnicas. Gerencia puede reabrir una obra suspendida/finalizada/cancelada con motivo, si no tiene facturas ni cierre comercial. La reapertura conserva los estados previos en el historial.
- El pago de la última factura y la nota de crédito que deja el saldo en cero llaman al flujo común `cerrar_obra_comercial`, con una sola transición y el mismo evento de auditoría.
- El dashboard incluye cartera total, vencida y antigüedad (1-30, 31-60, 61-90 y más de 90 días), recaudación neta de reversiones, carga de obras por técnico, top 10 clientes por venta/deuda, proyección restante de presupuestos aprobados, presupuestos que vencen en 7 días y conversión de decisiones.
- `cuentas_por_cobrar` es una foto al día de hoy y no depende de `desde/hasta`; `recaudacion_periodo`, ventas y conversión sí usan el periodo seleccionado. La proyección es el saldo aún no facturado de presupuestos aprobados dentro del periodo consultado; no equivale a flujo de caja garantizado.
- El endpoint se consulta bajo demanda; no usa WebSockets ni SSE. Aplica caché de 15 segundos por rol/filtros; `GET /api/dashboard/resumen/?actualizar=1` fuerza una lectura nueva y actualiza la caché, para conectar al botón “Actualizar Datos”. La caché predeterminada es local al proceso; en despliegue con varios workers se debe configurar un backend compartido (por ejemplo Redis).
- Los filtros de técnico/estado mantienen el alcance documentado: los KPI de presupuestos quedan limitados a presupuestos asociados a las obras que cumplen esos filtros; presupuestos aún sin obra quedan fuera de esos KPI.
- No se muestra margen/rentabilidad hasta acordar el criterio contable de ingresos y costos. No se agrega exportación CSV; Excel queda para una etapa posterior.
- Las numeraciones incluyen el año como referencia y un identificador secuencial global derivado de la clave primaria; el contador no se reinicia al cambiar el año.
- Los costos se congelan al finalizar o cancelar operativamente la obra, o al cerrarla comercialmente. Las observaciones técnicas siguen corregibles; Gerencia usa `POST /api/obras/{id}/reabrir/` con `motivo` para volver a `en-proceso`, solo si aún no hay factura/cierre comercial.
- `POST /api/obras/{id}/transicionar/` requiere `motivo` al pasar a `suspendida` o `cancelada`; cancelar se bloquea ante cualquier factura emitida.
- Indicadores dashboard adicionales en `metricas`: `cuentas_por_cobrar`, `recaudacion_periodo`, `proyeccion_ingresos_aprobados`, `presupuestos_por_vencer_7_dias`, `conversion_presupuestos`. En `distribuciones`: `obras_activas_por_tecnico`, `top_clientes_por_ventas` y `top_clientes_por_deuda`.
- El botón `Actualizar Datos` debe solicitar el resumen incluyendo `actualizar=1` para saltarse los 15 segundos de caché. La UI aún conserva datos de demostración hasta la integración frontend/API prevista para el siguiente punto.

SEGURIDAD Y AUDITORÍA - AJUSTES (2026-11)
----------------------------------------
- Access JWT dura 15 minutos; se mantienen refresh rotativo, blacklist, cookies HttpOnly y CSRF.
- Cada refresh valida de nuevo que el usuario exista, esté activo, no esté eliminado y conserve `estado=activo`. Desactivar una cuenta revoca su capacidad de refrescar; activarla/restablecer su contraseña invalida los refresh anteriores.
- Login aplica DRF `5/minuto` por IP y bloqueo temporal adicional por combinación IP/correo tras 5 fallos durante 15 minutos. No cambia permanentemente el estado de la cuenta, evitando que un tercero pueda bloquearla de forma indefinida.
- Gerencia puede crear cuentas en `/api/usuarios/`; si la cuenta queda pendiente o sin contraseña, `POST /api/usuarios/{id}/activar/` recibe la contraseña inicial y activa la cuenta. Ese endpoint también permite restablecer contraseña. Las contraseñas pasan por los validadores Django y nunca se escriben en logs.
- `AuditoriaLog` registra IP remota, user-agent y snapshots JSON antes/después en altas, cambios, borrados lógicos y workflows financieros/operativos. El encabezado `X-Forwarded-For` solo se acepta si `FYAG_TRUST_PROXY_HEADERS=true` y el proxy está controlado por el despliegue.
- El log es append-only en el modelo y manager: no permite save de registros existentes, delete ni QuerySet.update. `AuditoriaLog` no está registrado en Django Admin.
- `backend/.env.example` documenta la configuración de secretos, DEBUG, hosts y orígenes. `backend/.env` está ignorado por Git; `DJANGO_SECRET_KEY` es obligatorio y no hay clave por defecto. DEBUG queda apagado por defecto; para demo HTTP local se habilita solo en el `.env` local.
- Configuración regional: `LANGUAGE_CODE=es-cl`, `TIME_ZONE=America/Santiago`. Para probar desde móvil en la LAN, agrega la IP/host del servidor a `FYAG_ALLOWED_HOSTS` y el origen del frontend a `FYAG_FRONTEND_ORIGINS`.
- La base configurada en `settings.py` es PostgreSQL. Esa sección permanece a cargo del responsable de dependencias/base de datos; esta revisión no la modifica.
- Generar `DJANGO_SECRET_KEY` para el entorno real antes del despliegue. El `.env` local creado para desarrollo está ignorado por Git; no se debe copiar a otros ambientes. El límite temporal de intentos usa el cache local configurado por Django, adecuado para la demo de un proceso; con varios workers debe configurarse un cache compartido para que el bloqueo sea global.
- Rutas nuevas: `POST /api/usuarios/{id}/activar/` (solo Gerencia), `GET /api/presupuestos/{id}/historial-versiones/` y las rutas de workflow listadas arriba.
